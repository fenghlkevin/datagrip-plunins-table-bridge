# DataGrip 插件开发实践：用复制粘贴启动跨连接表复制

把开发库中的表复制到测试库，涉及的不只是搬运行数据：还要决定复制结构还是记录、目标表已存在时怎样处理，以及跨数据库类型时生成的 SQL 是否符合预期。我在开发 TableBridge 时，将这个流程拆成两个阶段：复制粘贴只负责选择来源和目标，真正写入由传输向导中的确认与执行负责。

如果平时使用 Navicat 处理数据库复制，也可以从这个例子了解 DataGrip 插件的实现方式。这里讨论的是安装在 DataGrip 中的插件，重点是 IDE 交互、对象引用和执行边界。

## 1. 只在数据库树中接管动作

IDE 中的复制粘贴有很多含义。SQL 编辑器需要复制文本，数据网格需要复制单元格；插件不能把这些动作全部接管。

TableBridge 使用 ActionPromoter 判断当前上下文。只有在数据库树中、对象可复制，或目标节点可接收且插件剪贴板有效时，才提升对应动作的优先级。其他上下文继续使用 IDE 原有行为。

这让快捷键保留用户熟悉的含义：在数据库树选中来源表并复制，然后在目标数据库或 schema 上粘贴。粘贴动作打开向导，尚不执行数据库写入。

## 2. 剪贴板保存对象引用

复制时把整张表的数据放进系统剪贴板，会混合选择阶段和执行阶段，还可能造成大量内存占用。因此当前实现保存的是对象引用。

项目级服务持有 SmartPsiElementPointer 列表，系统剪贴板中写入自定义 DataFlavor 的随机 token，同时提供普通字符串形式的对象名称。读取时先核对 token，再解析对象指针；如果对象已经失效，就不继续传输。

这里有三个边界：一次复制要求对象来自同一连接、同一模式；服务属于当前项目；复制操作并不生成数据快照，执行时才读取表记录。来源数据若在两阶段之间变化，用户不能把复制时刻当成数据快照时刻。

## 3. 用向导分离配置与执行

向导分为来源与目标、对象选择、传输审核三个步骤。对象选择阶段处理目标名称、复制范围和目标表已存在时的策略。默认策略是停止并提示，避免在用户未明确选择时覆盖已有目标。

![对象选择与传输设置](https://img2024.cnblogs.com/blog/3857882/202610/3857882-20261002215040115-987579150.png)

增量新增和更新保留目标独有记录；镜像新增、更新和删除会删除目标中来源不存在的记录。这两种语义必须在 UI 和审核摘要中说明，不能只用一个模糊的“同步”选项表达。

## 4. 把目标 SQL 展示给用户

跨库复制涉及类型、对象定义和依赖。当前支持范围内的 MySQL 与 PostgreSQL 转换会生成目标 SQL，向导在执行前展示目标位置、对象摘要、类型转换与依赖说明，并提供相应编辑能力。

![执行前审核目标 SQL](https://img2024.cnblogs.com/blog/3857882/202610/3857882-20261002215111598-919751275.png)

复杂视图、函数、过程、排序规则、高级索引和触发器可能需要人工处理。自动转换并不意味着任意 SQL 都能在两个数据库中等价执行，审核流程需要保留这些限制。

## 5. 验证和适用范围

当前版本仍为 alpha，兼容 DataGrip 2026.2（262.*）。已有实库验收记录覆盖 MySQL 8.0.43 与 PostgreSQL 18.3，以及支持范围内的同类型复制和两者之间的转换。Oracle 实现是未经本版本实库验收的实验性能力；SQL Server 不在当前支持范围。

开发中需要分别验证动作上下文、对象失效、目标表冲突和实际数据传输结果。界面演示只能说明配置路径，不能代替实库执行验证。文中的截图使用真实插件界面和示例元数据，不是完整数据库传输成功的证明。

删除重建与镜像同步会改变目标数据；部分数据库 DDL 可能隐式提交，失败后可能留下已创建结构。试用应使用可丢弃的数据，插件也不能替代数据库备份。
